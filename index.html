How these numbers are built

Model weights = params × bytes/param. Bytes come from the weight precision: FP16 = 2, FP8 = 1, FP4 ≈ 0.56 with its scales, INT4 = 0.5. As released uses the checkpoint's own mix; gpt-oss-120b, for example, ships MXFP4 experts with BF16 attention, 65 GB in all. Parameter counts include vision encoders and speculative-decoding heads, since those load too. This is fixed regardless of load.

KV cache is added up per kind of layer, from each model's config.json. A standard attention layer stores 2 × kv_heads × head_dim × bytes per token (the 2 is K and V). Sliding-window layers keep only their last N tokens. Latent attention (MLA) stores one compressed vector per token, and DeepSeek V4 keeps one entry per 4 or 128 tokens. Linear-attention and Mamba layers keep a fixed-size state per user (counted in fp32) that never grows with context, which is why hybrid models like Qwen 3.5+, Kimi K3 and Nemotron hold long contexts cheaply. Each user's cache is sized at prompt + reply, the most it holds, at the end of its reply; engines fill it as tokens arrive, so this is the peak. Total = one user's cache × users.

Activations = T × (hidden × 4 + ffn × 2) × 2 B plus users × vocab × 4 B of fp32 logits, where T is tokens per step — the prompt piece size set by Optimize for, or the number of users, whichever is larger. The MLP intermediate (ffn, 3.5–4× hidden for SwiGLU) dominates, which is why activations track the piece size rather than context length. Compute stays bf16 even when weights are quantized, and FlashAttention keeps the T² score matrix off HBM — so there is no quadratic term. Genuinely the smallest of the four on most configs; choose Fast first reply to see it grow.

Overhead = a fixed ~1.0 GB CUDA/driver context plus a slider % of the three above, standing in for allocator fragmentation, framework buffers, and CUDA graphs.

Tensor-parallel overhead — the page picks TP for you as part of the smallest layout, fixed in Advanced settings if you prefer. With TP > 1 the model is sharded across GPUs: weights and activations divide by TP, and the KV cache divides by min(TP, kv_heads). Sharding adds memory: every GPU carries its own ~1 GB CUDA context, plus NCCL all-reduce workspace and comm buffers (~0.3 GB + users × hidden × 8 B per GPU). When TP exceeds a layer's KV heads, that part of the cache can't split further and copies to every GPU — watch it stop shrinking. Latent and compressed caches have a single head, so they always copy; linear-attention state splits cleanly.

Throughput — generating a token means reading this GPU's weight shard plus every active request's KV cache, so a decode step takes bytes read ÷ (memory bandwidth × 0.65). At very large batches the compute cost users × 2 × active params ÷ (FLOPs × 0.5) takes over, so the step uses whichever is slower. Tensor parallelism adds two all-reduces per layer, sized to the batch's activations and sent over NVLink or PCIe, and the engine adds ~1.5 ms per step. Output = users ÷ step time. Reading a prompt is compute-bound: prompt × (2 × active params + layers × prompt × hidden) ÷ (FLOPs × 0.45). The prompt is read in pieces (512, 2,048 or 8,192 tokens, set by Optimize for), and each piece shares a step with everyone else's next token. So time to first token = prompt compute + pieces × step time, and the pause other users feel = one piece's compute + one step. Smaller pieces mean more steps before the first reply but shorter freezes. Requests are assumed to be halfway through their reply (prompt + half the reply in cache), and the first reply waits on the whole prompt. Quantized weights read fewer bytes but lose some of that gain to dequantization; FP8 also speeds up compute on boards with native FP8 cores. MoE models read more experts as the batch grows. Bandwidth and link speeds are published specs; FLOPs are rough estimates.

Thinking — a model that reasons step by step writes thinking tokens before its answer. They're generated like any other token, so a user's cache peaks at prompt + thinking + reply, speed is judged halfway through thinking and reply together, and cost per output token counts them. First reply is when the first token appears, which for a thinking model is the start of its thinking; the stat also says how long the thinking runs before the answer begins. Earlier turns' thinking is normally dropped by the model's chat template, so it doesn't build up in the prompt. The switch starts at each model's own default, taken from its model card and chat template.

Concurrent users from traffic — requests in progress at once = requests per second × seconds each one takes. A request takes the wait before its first token plus its thinking and reply, streamed at your speed goal's rate; the goal is a minimum speed, so this errs on the high side. The busiest-hour multiple covers traffic that isn't spread evenly through the day; 2× suits a typical workday.

Sharing — on a hosted copy of this page, the address always holds the current settings, so Copy link sends the exact scenario. Download summary saves a one-page report of the recommendation, the inputs and every board, which prints to PDF.

Suggestion and capacity — every board is tried at 1, 2, 4 and 8 GPUs per copy (splitting a copy only across NVLink boards), with as many copies as it takes to serve every user. The suggestion is the setup that reaches the speed goal with the least GPU memory in total (on any one board, the fewest GPUs); if none reaches it, the one that comes closest. Handles up to is the most users the setup holds at the current prompt and reply lengths while fitting in memory and, with a goal, still reaching it.

Copies (replicas) — for more users, the page runs more copies of the model instead of splitting one copy wider. Each copy has its own GPUs and an even share of the users, so memory, the bar and the breakdown describe one copy, while GPU count, output and capacity add up across all of them. Copies don't exchange data while generating, so they need no NVLink and can run on separate servers; that's why PCIe boards scale out well even though they split a single copy poorly, and why, when two layouts use the same number of GPUs, a PCIe board takes more copies over splitting one. When a board needs more GPUs than memory alone calls for, the extra ones are there to reach the speed goal, and the page says so. This assumes a load balancer spreads requests evenly.

Units — every amount is computed in bytes and shown in the unit picked at the top: GB is 10⁹ bytes (spec sheets, download pages), GiB is 2³⁰ bytes (nvidia-smi, PyTorch and vLLM's logs). Switching changes the labels, never the answer. Board capacities are the size on the box, counted as GB, so an H100 is 80 GB or 74.5 GiB. Real boards expose that much or slightly more, so a fit here errs on the safe side.

Estimates for planning, not a guarantee. Real usage varies with the serving framework (vLLM, TensorRT-LLM, SGLang), paged-attention block sizing, speculative decoding, and MoE routing. MoE models load all expert weights even though only a few activate per token. The newest attention designs (DeepSeek V4's compressed sparse attention, sparse-attention index keys) are modeled from their configs, so treat those cache figures as ±25%.
